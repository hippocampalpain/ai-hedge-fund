# 한국 모드: 데이터 출처와 계산식

코드 위치: `hedge_fund/data/kr/fundamentals.py` (계산), `hedge_fund/data/kr/accounts.yaml` (계정 매핑)

## 1. 기본 원칙

| 원칙 | 구현 |
|---|---|
| 미래 데이터 누설 금지 | 기준일 `D`에는 DART 접수일(`rcept_no` 앞 8자리 = `rcept_dt`)이 `D` 이하인 보고서만 읽는다. **계산하기 전에** 거른다. 아직 끝나지 않은 분기의 보고서는 요청하지도 않는다. |
| 값을 지어내지 않음 | 입력이 하나라도 없으면 결과는 `None`. 0으로 채우지 않는다. |
| 연결 우선 | 보고서마다 연결재무제표(CFS)를 먼저 찾고, 없으면 별도재무제표(OFS)를 쓴다. CFS와 OFS끼리는 절대 빼거나 더하지 않는다. |
| 통화 | 모든 금액은 원(KRW). `currency="KRW"`. |

## 2. 누적값 → 분기값

DART 가이드에 따르면 분기·반기 보고서의 손익계산서는 `thstrm_amount`가 3개월 금액, `thstrm_add_amount`가 누적 금액이다. 현금흐름표는 누적으로만 공시된다. 그래서 손익·현금흐름 항목은 **항상 누적 금액을 읽고** 빼서 분기 값을 만든다.

```
1분기 = 1분기보고서(11013) 누적
2분기 = 반기보고서(11012) 누적 − 1분기 누적
3분기 = 3분기보고서(11014) 누적 − 반기 누적
4분기 = 사업보고서(11011) 연간 − 3분기 누적
```

빼는 쪽 보고서가 없으면 그 분기의 손익·현금흐름은 `None`이다. 재무상태표 항목은 각 보고서의 기말 잔액을 그대로 쓴다.

## 3. TTM과 공시일

- **TTM(최근 12개월)** = 연속된 4개 분기의 합. 4개 중 하나라도 없으면 그 행은 만들지 않는다.
- **행의 `filing_date`** = 그 행을 만드는 데 쓴 보고서 중 **가장 늦은 접수일**.
- **평균 잔액** = (이번 분기말 + 4분기 전 분기말) ÷ 2. 4분기 전 값이 없으면 평균을 쓰는 지표는 `None`이다.
- **유통주식수**: DART 「주식의 총수 현황」의 유통주식수(발행주식 − 자기주식), 보통주+우선주 합계. 이 값은 반기·사업보고서에만 있고 1·3분기 보고서에는 `-`로 나온다. 그래서 1·3분기는 직전에 공시된 반기·사업보고서 값을 이어 쓴다. BPS·PSR·주당FCF의 분모다.
- **가중평균 발행주식수** (EPS의 분모): 같은 표의 발행주식총수(`istc_totqy`, 자기주식 포함), 보통주+우선주 합계. 반기·사업보고서 값 사이의 분기말은 직선으로 잇고(보간), 마지막 값 뒤는 그대로 이어 쓰고, 첫 값 앞은 첫 값을 쓴다. 기간 평균은 분기말 값으로 사다리꼴 평균: TTM이면 `(S0/2 + S1 + S2 + S3 + S4/2) / 4`. **평가일까지 공시된 보고서만** 쓰므로, 아직 공시되지 않은 사업보고서의 주식수로 보간하는 일은 없다. 발행주식총수가 없으면 기말 유통주식수로 나눈다.

## 4. 지표 계산식

| 지표 (필드) | 계산식 |
|---|---|
| EPS `earnings_per_share` | TTM 지배주주순이익 ÷ 가중평균 발행주식수 (보통+우선, 와이즈리포트 정의) |
| BPS `book_value_per_share` | 지배주주지분 ÷ 유통주식수 |
| PER `price_to_earnings_ratio` | 종가 ÷ EPS (EPS ≤ 0이면 None) |
| PBR `price_to_book_ratio` | 종가 ÷ BPS (BPS ≤ 0이면 None) |
| PSR `price_to_sales_ratio` | 종가 ÷ (TTM 매출 ÷ 유통주식수) |
| ROE `return_on_equity` | TTM 지배주주순이익 ÷ 평균 지배주주지분 |
| ROA `return_on_assets` | TTM 당기순이익 ÷ 평균 자산총계 |
| ROIC `return_on_invested_capital` | 영업이익 × (1 − 법인세비용/세전이익) ÷ (자본총계 + 차입금 − 현금성자산) |
| 부채비율 `debt_to_equity` | 부채총계 ÷ 자본총계 (배수. 네이버 % 값 ÷ 100) |
| `debt_to_assets` | 부채총계 ÷ 자산총계 |
| 유동비율 `current_ratio` | 유동자산 ÷ 유동부채 |
| 당좌비율 `quick_ratio` | (유동자산 − 재고자산) ÷ 유동부채 |
| `cash_ratio` | 현금및현금성자산 ÷ 유동부채 |
| `operating_cash_flow_ratio` | TTM 영업활동현금흐름 ÷ 유동부채 |
| 매출총이익률 `gross_margin` | 매출총이익 ÷ 매출 (매출총이익 계정이 없으면 매출 − 매출원가) |
| 영업이익률 `operating_margin` | 영업이익 ÷ 매출 |
| 순이익률 `net_margin` | 당기순이익(비지배 포함) ÷ 매출 |
| FCF | 영업활동현금흐름 − \|유형자산의 취득\| |
| `free_cash_flow_per_share` | FCF ÷ 유통주식수 |
| `free_cash_flow_yield` | FCF ÷ 시가총액 |
| 시가총액 `market_cap` | 가격 기준일(또는 그 직전 거래일)의 KRX 시가총액 (보통주) |
| 차입금 | 단기차입금 + 유동성장기부채 + 장기차입금 + 사채 (있는 계정만 더함, 하나도 없으면 None) |
| EV `enterprise_value` | 시가총액 + 차입금 − 현금성자산 |
| EBITDA | 영업이익 + 감가상각비 (+ 무형자산상각비). 감가상각비가 현금흐름표 본문에 없으면 None (삼성전자는 주석에만 있어 None) |
| `enterprise_value_to_ebitda_ratio`, `enterprise_value_to_revenue_ratio` | EV ÷ EBITDA, EV ÷ TTM 매출 |
| `peg_ratio` | PER ÷ (EPS 성장률 × 100), 성장률 > 0일 때만 |
| 성장률 `*_growth` | 이번 TTM ÷ 4분기 전 TTM − 1 (기준값 ≤ 0이면 None) |
| `payout_ratio` | \|배당금 지급\| ÷ TTM 지배주주순이익 |
| 회전율 | 매출(재고는 매출원가) ÷ 평균 자산·재고·매출채권·운전자본. DSO = 365 ÷ 매출채권회전율 |
| `interest_coverage` | 영업이익 ÷ 이자비용 — 이자비용이 손익계산서 본문에 따로 있을 때만 (대부분 None) |

지배주주순이익이나 지배주주지분 계정이 없으면(별도재무제표 등) 당기순이익과 자본총계를 대신 쓴다.

**가격 기준일 (PER·PBR·PSR·시가총액·EV·FCF yield·PEG):**

- **가장 최근 행** = 평가일(기준일) 종가 ÷ 평가일까지 공시된 최신 재무. 백테스트에서는 리밸런싱하는 거래일의 종가다(그날 종가에 판단하고 다음 거래일 종가에 체결).
- **과거 행** = 그 행의 공시일 종가. "그 숫자가 나왔을 때의 밸류에이션" 이력이다.
- 그래서 같은 보고서를 보는 기간에도 평가일마다 최신 행의 PER·PBR이 바뀌고, LLM 프롬프트도 날짜마다 달라진다(캐시 적중 없음).

**스냅샷에 P/B를 직접 넣는 이유:** 이전 버전 프롬프트에는 P/B가 없어서 graham이 `P/E × ROE`로 짐작했다(삼성전자 2026-10-23: 12.04 × 0.31 ≈ 3.7). 이 프로그램의 ROE는 *평균* 자본 기준이라 이 곱은 기말 BPS 기준 PBR(당시 공시일 기준 3.19, 평가일 기준 2.50)보다 크게 나온다. 지금은 P/B 열을 그대로 준다.

## 5. KRX·네이버 값과 비교할 때 주의할 점

삼성전자, 기준일 2026-11-06, 2025년 사업보고서 행으로 검증한 결과:

| 항목 | 이 프로그램 | 비교 대상 | 차이 |
|---|---|---|---|
| 부채비율 | 29.94% | 네이버 29.94% | 일치 |
| ROE | 10.85% | 와이즈리포트 10.78% | 0.07%p (평균 자본 계산 방식) |
| BPS | 63,997 | KRX·네이버 63,997 | 일치 |
| EPS | **6,557** (이전 6,676) | 와이즈리포트 6,564 / KRX·한경 6,605 | 와이즈리포트 대비 −0.11% |

- 와이즈리포트 EPS = 지배주주순이익 ÷ 수정평균발행주식수(보통+우선). KRX EPS = 회사가 공시한 보통주 기본주당이익(DART 손익계산서 `ifrs-full_BasicEarningsLossPerShare` = 6,605).
- 남은 0.11% 차이: 실제 가중평균은 자기주식 소각일 기준 일할 계산이다. DART 공개 API의 증자(감자) 현황(`irdsSttus`)에는 삼성전자의 이익소각 일자가 나오지 않아(전부 `-`), 반기·연말 발행주식수를 직선으로 이은 근사값을 쓴다.
- KRX와 네이버의 PER은 "오늘 종가 ÷ 직전 사업연도 EPS"다. 이 프로그램의 최신 행 PER은 "평가일 종가 ÷ TTM EPS"다.

| 날짜 | 네이버 표시 종가 (= FDR) | 네이버가 다음 날 전일비 계산에 쓴 전일 종가 | pykrx (KRX) |

| 11-04 | 221,500 | 218,000 | 218,000 |
| 11-06 | 193,500 | (아직 없음) | 188,700 |

- 시가·고가·저가·거래량은 거의 같고 **종가만** 11/14일 다르다. 그런데 네이버가 표시하는 "전일비"·"등락률"은 13일 모두 **KRX 종가(= pykrx)** 를 기준으로 계산돼 있다. pykrx 종가는 KRX 등락률·시가총액(= 종가 × 상장주식수)과도 맞는다. 와이즈리포트의 "전일종가 225,000"도 10-30 KRX 종가다.
- 네이버 표시 종가의 정체(대체거래소 NXT 애프터마켓까지 합친 통합 시세의 마지막 체결가로 추정)는 확인하지 못했다. 같은 숫자가 `fchart.stock.naver.com`, `api.stock.naver.com`, `m.stock.naver.com` 세 경로 모두에서 나오므로, 수정주가나 시간대 차이는 아니다(이 기간에 액면분할이 없고 하루 밀림도 없다).
- 옛 `finance.naver.com/item/sise_day.naver` 페이지는 2026-11 현재 HTTP 410 "더 이상 제공되지 않습니다"다.
- 그래서 pykrx를 쓰지 못해 FDR로 넘어가면 경고 로그를 남긴다.

한 경로가 실패하면 다음 경로를 시도한다. 모든 경로가 실패하면 빈 값이 아니라 **오류를 낸다**. "데이터 없음"과 "접속 실패"를 구분해서, 백테스트가 실패를 "신호 없음"으로 잘못 읽지 않게 하기 위해서다.

캐시는 `~/.hedge-fund/cache/kr/` 아래에 있다 (Windows: `C:\Users\<이름>\.hedge-fund\cache\kr\`).
- DART: 공시된 보고서는 영구 보관. "아직 없음"(013)은 최근 2년 이내 연도면 하루 뒤 다시 묻는다.
- 시세: 연도 단위로 저장.
- DART 호출 간격은 기본 0.3초(`DART_MIN_INTERVAL`). 실패하면 2초, 4초, 8초 간격으로 재시도한다.

## 8. 한계 (1차 버전)

- **12월 결산 법인만 재무지표를 제공한다.** 다른 결산월이면 빈 목록을 돌려주고 경고를 남긴다(분기 해석을 추측하지 않기 위해).
- **뉴스는 제공하지 않는다.** **실적 서프라이즈(컨센서스)도 무료로 구할 수 없어서** PEAD 모델은 한국에서 항상 중립이다.
- **정정공시:** DART 전체 재무제표 API가 정정 후 숫자를 돌려주는 경우, 원래 공시일 기준으로 아주 약간의 누설이 있을 수 있다.
- **주가 기준이 섞일 수 있다:** pykrx는 수정 전 주가, FDR(네이버)은 수정주가다. 액면분할이 있었던 종목은 경로에 따라 과거 가격 기준이 다를 수 있다.
- **업종 정보는 최신값을 쓴다** (과거 시점 값이 아님. 미국 모드와 같은 근사).
- **분 단위 펀드는 지원하지 않는다**(일봉만).
- **시가총액 분위표:** 미국 달러 기준 표라서 한국 모드에서는 쓰지 않는다. 블라인드 프롬프트에 크기 정보가 나오지 않는다.
- **TUI 화면의 `$` 표기는 그대로다** (금액은 원화).

## 9. 백테스트: 평가일과 LLM 호출

- **평가일은 거래일만이다.** 리밸런싱일(거래일) 종가에 판단하고 다음 거래일 종가에 체결한다. 체결 전 "새로 고침" 기준일은 체결일의 *직전 거래일*(= 판단일)이라서, 금요일에 판단하고 월요일에 체결할 때 일요일을 평가하는 일이 없다. (이전 버전은 달력상 전날을 써서 2026-10-25(일)에 LLM을 한 번 더 불렀다.) 모의투자(`aihf paper`)도 한국 모드에서는 KOSPI(벤치마크)의 직전 거래일을 기준일로 쓴다(주말·KRX 휴장일 건너뜀). 미국 모드에 미치는 영향은 `03_us_mode_impact.md`.
- **예상 LLM 호출 수** = LLM 에이전트 수 × 종목 수 × 평가일 수. 평가일마다 최신 행이 그날 종가로 다시 계산되므로 날짜마다 새 프롬프트다. 이미 성공한 호출은 캐시에서 읽으므로 같은 조건으로 다시 돌리면 그만큼 빠진다. 재시도는 세지 않는다.
- **Gemini 재시도:** 429/RESOURCE_EXHAUSTED는 최대 6회(`LLM_MAX_RETRIES`). 500/502/503/504, `Deadline expired`(DEADLINE_EXCEEDED), UNAVAILABLE, 타임아웃·연결 끊김은 최대 3회(`LLM_TRANSIENT_RETRIES`). 둘 다 5초, 10초, 20초 … 지수 백오프에 1초 이내 지터가 붙는다(`LLM_RETRY_BASE_SECONDS`, `LLM_RETRY_MAX_SECONDS`).
- **Gemini 요청 제한 시간:** 기본 180초(`GEMINI_TIMEOUT_SECONDS`). 이전 60초에서는 `gemini-flash-latest`가 긴 프롬프트에 504 `Deadline expired`를 냈다.
- **데이터 캐시 버전:** 백테스트의 디스크 캐시(`~/.hedge-fund/cache/data/`)는 `(종목, 기준일)`로 재무지표를 저장한다. 계산식을 바꾸면 `KRDataClient.cache_version`을 올려서 옛 계산값이 다시 쓰이지 않게 한다(현재 `kr-2`). 미국 모드 캐시 키는 그대로다.
